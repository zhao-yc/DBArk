## 原正式失败

`run1508-upsert-ui` 为 Windows 开发 Electron、准确 MySQL 8.4.11／明文专用 13384。Root 先核 200 宿主及实例 UUID、随机库创建前不存在，再预建唯一带标记的 subject 空表：id、note、created_at。用例从真实表单建立不保存密码的连接，打开同库查询，通过键盘输入 VALUES 新行别名语句；不执行正文，不调用旧剪贴板输入帮助器。

正式单次失败：点号后 13 秒内没有建议窗口，尚未达到三列建议及精确插入验收。原 SQLite 只读核对确认 SQL 完整落盘，末尾为 ASCII `note=incoming.`，默认库准确、执行历史为零。不能仅凭 RAM 的 ready 结果把此身份视为通过。

## 有界诊断及实际原因

独立 `run1511` 只旁观真正 NativeWorker，`run1513` 再旁观原 Main IPC。副本位于私有忽略目录，原正式用例、Worker 请求／响应、产品代码、期限及点号触发保持；没有加 Ctrl+Space 或失败重试。只记录长度、偏移、能力布尔、状态、命令种类、结束及脱敏错误，不收集 SQL、认证或元数据行。

- 两次真实 Worker 请求（输入末字、再输入点号）均启用 insertRowAliases，两次实际响应均 ready、一个目标关系；握手完成，无 Worker error 或 terminate。
- 真实 connections.open 成功，版本为 8.4.11。
- 第一列目录请求的前缀长度为 8，随后点号编辑取消该请求，query.cancel 成功。
- 第二列目录请求的前缀长度为 0，实际 Main 回复：`独立任务物理资源尚未确认释放，请显式断开连接；原操作未重放`。DOM 同时显示“补全目录暂不可用”。
- 原生旁观计数 query.execute＝0、sessions.open＝0。

该错误与独立 RAM 反例对上：三列查询成功后，非严格 QUIT 回调先到、原流 close 尚未到，资源账本拒绝交付。修复应让目录入口使用已有真正严格收尾；资源保护门、未知保留及不重放保持。当前固定正式头仍失败，修正后的正式无旁观复验继续。
