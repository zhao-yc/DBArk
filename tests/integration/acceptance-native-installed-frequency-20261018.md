## 原失败与修正

- run1499 在安装前把 event_scheduler Daemon 也当成客户端残留，前置失败，没有执行安装器。Root 双重复核原 PID／TCP 四元组、用户及实例后，仅 KILL 本例空闲控制线程一次；另读确认线程消失并严格关闭诊断原流。run1501 为控制器生成时的引号语法错误，实际操作为零。两者保留原件，新编号改为准确分类守护线程。
- run1502 的 JSON 身份在输入凭据及执行 SQL 前，因为 Field 包装的 select 标签含选项文字，exact label 找不到而失败。Root `a49537a` 只修两个下拉框为本对话框的 role／标签前缀，增加唯一数量及精确选中值断言；生命周期、期限和产品不变。
- run1505 已实际导出 JSON，随后原数字 ID 期待失败。独立 run1506 用同字节 SELECT 和生产精度配置确认协议 ID 类型为 LONGLONG，原 mysql2 和原导出均为字符串；BIGINT／小数、NULL、二进制断言同时通过。Root `d145fd2` 改为精确期待字符串，未放宽成数字转换，未修改产品精度策略。原红和原文件保持，CSV 当时未运行。

后续 run1507 固定测试头 `d145fd2`，仍使用原安装的相同 EXE／asar／helper 字节。该头的后续补全、锁原语源码未在旧安装中，不由本批接纳。

## 收尾及摘要

两项成功后，独立控制连接重新核准确实例、自有前缀临时库和全部客户端线程均为零；event_scheduler 仅作为守护线程准确分类。控制连接同一原流严格 close，各例应用正常退出、所属 PID 不存在且临时用户目录移除。再核安装资源不变，执行本例卸载器并等待真实 close／退出码 0；注册及 DBArk 进程归零，自有安装目录移除。旧失败测试的私有诊断目录保留，没有把未知资源从 finally 强删。
