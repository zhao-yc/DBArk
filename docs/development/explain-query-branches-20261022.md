# 执行计划查询分支包装（2026-10-22）

## 问题与行为

MySQL 实际 JSON 计划的 `query_specifications` 数组项可能同时包含 `dependent`、`cacheable` 和 `query_block`。原解析器只展开单键包装，多键项会保留成名为 `0`／`1` 的未知节点，用户无法分辨这是查询分支还是未知优化器操作。

现在对 `query_specifications`、`subqueries`、`attached_subqueries`、`optimized_away_subqueries`、`having_subqueries` 和 `select_list_subqueries` 六个已知数组，识别含自有对象 `query_block` 的实际包装层，显示“查询分支 · 第 1 项”或“子查询项 · 第 1 项”。单键包装同样保留，子查询块仍单独呈现；项号只表示 JSON 数组位置，不表示执行次序。

包装自身的 `dependent:false`、`cacheable:true`、其它原始属性及估算指标分别保留，不移动给子块，也不把父子成本相加。完整标题可用于本地查找，跳转会展开祖先并聚焦准确包装节点；详情按原路径读取原包装，而非只显示里面的查询块。

## 保真与边界

- `kind` 保留原数组索引，另加受限 `arrayEntry` 元数据描述容器和零基位置；不把语义名称添加到通用已知操作集合。
- 只有六个已知数组及自有对象 `query_block` 可识别。非法成员、错类型子块或未知扩展仍保留真实索引／原文与未知告警，不能为消除警告而猜测类型。
- 普通连接和窗口数组仍沿用原展示规则；原 JSON Pointer、包含关系、数组顺序、精确数值、完整原文和全部预算保持。
- 标题只使用节点自有、合法的容器及安全整数位置；继承字段或 getter 不会获得标题授权。展示层不改写解析器的未知标志。
- 仍最多 300 个节点；多保留的真实包装层占用同一预算，超限明确提示，未展示内容从原文查看。搜索的 200 字限制及计划换代／旧事件隔离保持。
