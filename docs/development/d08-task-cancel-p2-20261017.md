# D08任务中心重开后的取消状态修复

父提交为 `4c15e06713f67f2ed37318b3932e7bb9a1ff190b`，本笔与核心回执 `e3a1532f96f732ddf90524e43db0b9c2dc0f0ce0`、实库定义和接线材料分别提交。

## 问题与结果

旧任务面板只在挂载后监听COMMIT事件。COMMIT早于打开窗口时，局部集合从空开始，仍显示“取消任务”；引擎虽然正确拒绝KILL，界面却误导用户。本次让界面先订阅，再读取当前主进程内存的可信状态；重开窗口、读取失败或阶段尚未核验时保守关闭取消。

新增只读命令 `tasks.cancelState`，输入最多200个有界任务编号，只返回编号及固定枚举 `allowed/checking/confirming/finished`。校验器、契约、预加载白名单和主进程分发同步接入。没有新增事务执行命令、持久化字段、SQL、目标或错误详情。

主进程只依据当前 `tasks` 内存记录及其主进程签发的回执关联。普通运行中查询保留取消；数据提交还须匹配当前内存回执、处于执行阶段且事务保护、事务已知和事务打开均成立。COMMIT可能已发送立即关闭取消。历史任务没有当前记录时保持待核验。辅助SQLite写盘失败不会使内存COMMIT状态降回磁盘中的旧执行阶段。

## 竞态和生命周期

- 每次挂载建立独立控制器，订阅先于初值读取。每个列表项采用单调版本，读取期间到达事件时旧响应无效；编号移除后重加不能冒领旧响应。
- 同时仅一个读取，事件和列表变化合并补读，没有轮询、计时器或人为延时。COMMIT及终态锁定后，迟到的可取消快照和普通事件不能重新开放取消。
- 请求失败、重复编号、额外字段和畸形响应保守处理。未核验项明确提示“尚未核验当前阶段，暂不能取消”。
- 卸载先停用控制器再解绑订阅，迟到结果不能更新状态或继续补读。点击入口再次检查控制器当前值，旧渲染闭包不能在已收到COMMIT事件后发送取消。

没有改引擎COMMIT/ACK/KILL语义，没有解析消息文案，没有重放入口。没有修改正式TableTab、recordViews、QueryTab、App或store。
