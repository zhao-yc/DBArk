# 表文件导出提交窗口的取消修复

## 问题与修复范围

员工2的独立RAM反例确认，`88fabaf3ab1248771373e72873c6cc229bf323df` 的选列CSV与其父提交 `f9dfa3c4f877b6b58f218d3d8c1b69b451014f71` 的默认全列CSV都有继承的取消窗口：文件同步等待时接受了取消，随后仍执行重命名替换原件，最终任务却报告 `cancelled`。这不能作为原文件受保护的成功验收。

`9b2bf87` 首次仅修CSV；Root随后指出JSON与SQL使用相同的提交实现，独立追加的RAM反例也确认了相同缺口。最终修复覆盖 `Engine.exportFile` 中 `files.export` 的CSV、JSON、SQL三格式，不再按CSV限定：

1. `file.sync()`、`file.close()` 每次等待完成后重新检查取消。此时接受取消则清理本任务partial，保留原件，不调用rename。
2. 最后一次检查与设置既有 `task.fileCommitStarted` 屏障同步完成，中间不让出执行权，然后只发送一次rename。
3. rename已开始时，现有取消协议不再将任务标记为取消。等待该次真实替换结果：成功报告完成，失败报告失败；不自动重试或再次rename。取消请求返回不等于文件任务已终态，调用方仍应等待原导出任务结束。

复用原任务取消、最终状态与资源收尾，不扩展协议或框架。三种格式的参数、字节编码与序列化未变；共同的提交窗口统一修正。Excel、任意SQL完整导出、已返回结果和CSV ZIP使用其它实现，本片未改，也不声称其所有提交窗口已获验证。没有修改版本或标签，不移动已有0.20标签；该继承问题的修复由后续版本接纳，旧发布仍按已知问题处理。
