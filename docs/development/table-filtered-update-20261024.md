# 当前筛选范围的跨页批量修改

## 使用方式

在表数据页应用筛选后，选择“批量修改服务器全部筛选行”。选择一个普通可编辑字段并输入值，点击“读取全部匹配行并预览”；核对准确匹配行数、库表、字段、时区和 SQL 样本，再输入 `数据库.表 / 字段 / 行数` 并勾选风险确认，明确提交。

范围来自当前已加载页面的完整筛选树和多列排序，包括停用条件和嵌套分组；不受当前页、当前勾选行或结果显示上限限制。无筛选表示全表。存在待提交草稿、活动单元格编辑或其它表任务时不能开始。普通的当前页勾选行填充入口保持独立。

## 数据与事务边界

- 预览以独立只读事务流式冻结全部原行，快照存于 Engine 私有临时文件，不将全表加载到渲染进程。最多两个预览；有效期从预览完成起十分钟。仅显示最多十行、256 KiB SQL 样本，明确标记省略，但实际修改覆盖全部冻结行。
- 仅支持可证明无触发器副作用的 InnoDB 普通表，要求可靠、非空且完整的唯一定位键；所有索引字段、自增和生成字段不可作为赋值字段。该保守限制防止外键级联修改预览范围以外的表；索引依赖不完整，或索引字段会因生成表达式／自动更新时间间接变化时整表拒绝。不可靠键、MyISAM、视图或无法证明元数据与权限时整份拒绝。
- 单字段上限 8 MiB、单行 16 MiB、全局快照 10 GiB，超限整体拒绝，不静默截断。BIGINT、DECIMAL、日期时间、二进制及 NULL 保留类型和原精度。
- 提交前重核实际服务器、表定义、原时区及快照文件身份和摘要；每行用可靠键及全部旧值核对。任一冲突、警告或事务保护失效导致整批回滚；预览后新增的匹配行不属于旧快照，需新预览才能修改。
- TIMESTAMP 保留原筛选时区，并增加内部 epoch 比较，避免只用格式化墙钟值定位。MySQL 的依据见[官方日期时间函数文档](https://dev.mysql.com/doc/refman/8.0/en/date-and-time-functions.html)；各支持版本仍以实际专项结果为准。
- 预览令牌绑定原窗口文档、连接修订及断开代次，应用只消费一次；取消等待原请求、实际取消及临时文件清理。COMMIT／ROLLBACK 回应未知时显示不确定结果，不自动重试；已收到的真实 COMMIT 回执不会被迟到导航或取消改写。

正常释放、到期及退出均等待临时文件清理。强杀 utility process 后遗留文件的自动回收尚未实现，不宣称异常退出后文件已经删除。父页筛选、排序和选中保持；只有确认提交且原来源仍有效时刷新原页。

## 验证入口

单元测试为 `tests/unit/*table-filtered-update*.test.ts(x)`。实库专项 `tests/integration/table-filtered-update.test.ts` 默认关闭，需同时设置 `DBARK_INTEGRATION_ENABLED=1`、`DBARK_TABLE_FILTERED_UPDATE_TEST=1` 及已核对的专用连接；默认与列表不读取凭据。

源码窗口专项 `tests/e2e/table-filtered-update.spec.ts` 另需 `DBARK_TABLE_FILTERED_UPDATE_UI_TEST=1`、随机资源标记、完整启动文件摘要及独占输出目录。测试使用 81 行、61 个跨页匹配，覆盖取消预览、整批提交和第 31 行并发冲突后的完整回滚；不使用剪贴板。

交叉审查另外修复了两个实际边界：临时连接保存锁不得因旧进度抵达而取消原任务；索引列可能通过外键级联修改其它表，因此本轮保守限制为无索引字段并新增 30 项回归。实库测试成功用例也显式结束原生命周期，避免误拦截同进程下一例。源码修正后重新冻结并完整检查。

下一轮 MySQL 5.7 主场景通过 61 行提交、并发冲突回滚和新增行隔离，且完成精确清理；取消场景的旧观察器在 `pending=1` 处失败。单次只增日志、不改断言的诊断确认：原 UPDATE 回调返回，但 mysql2 在 KILL 断链后不发命令 `end`；原同一物理连接、严格关闭和快照清理均已真实结束。原失败、诊断及随后独立原行／定义／零线程事务核对和精确清理分别记账，均不充当正式通过证据。

为此新增专项收尾证明和 39 项单元回归。正常路径仍要求原回调及命令 `end`；特殊路径必须捕获原 LOCK WAIT 中的连接和 UPDATE 对象、准确 KILL 的成功取消与控制连接原回调／end、原 UPDATE 回调、同一物理连接严格关闭、原线程及事务消失，以及原任务未知结果／无提交与回滚 ACK，才单列为 `physical-close`。原始 `pending=1`、`terminal=false` 不改写，不把物理关闭说成正常命令 end；缺任何证明仍失败，共享旧观察器保持。

首轮 Windows 窗口已完成取消预览和 61 行提交；Root 的准确单次并发修改返回后，独立测试脚本在写 ACK 前停止，第三次修改未点击。原 CAS header 未持久化；恢复中的同语义只读比较实际产生两条 1287 BINARY 弃用警告，不能据此补造原 header。新的 Root 测试 SQL 使用等价显式 CAST，仍要求零警告，并先保存完整 header 和两端协调错误。此处只改测试控制脚本，产品不变。

原窗口未证正常退出；独立确认批准进程不存在，完整 81 行含准确并发值、原定义／标记与零线程保持后，精确清理该库并严格关闭恢复连接。期间恢复脚本分别因 MySQL 8.4 展开式全局权限和精度配置返回字符串 `0` 的夹具预期失败，均未发送 DROP；准确处理实际权限枚举和类型后才完成核对清理，原失败保持。

取消观察仅在原有 120 秒 owner 内，持续查询原线程的 PROCESSLIST 与 INNODB_TRX，直到两个结果真正为空；记录首次和最终结果及观察次数，不延长期限、不重发取消或写操作。严格收尾分类器与 39 项单元断言保持。
