# SQLite 现有表 CSV／JSON 导入

## 使用流程

打开 SQLite 的普通表，在表页选择“导入 CSV／JSON”。表格有未提交草稿或运行中操作时先处理原草稿，不借导入覆盖它；视图、虚拟表和影子表不提供导入写入能力。

1. 选择 CSV 或 JSON、UTF-8／UTF-16LE／GB18030；CSV 可选逗号、分号、Tab 及有无标题。通过原生文件选择器领取导入令牌，不输入任意路径。
2. 完整检查原文件，查看联合源字段、准确目标列、总记录数和最多 20 条样本。样本不代表完整文件已经通过字段映射验证。
3. 明确添加源字段、目标字段及动态类型映射；不添加的目标字段走数据库默认规则。生成列不可映射，必填无默认且非自动生成的目标不能遗漏。
4. 按映射重新预检完整文件。报告显示实际检查数、有效／无效记录、问题总数和前 100 项明细；读取未完成、映射错误或空文件均不能取得提交能力。记录编号是从 1 开始的逻辑数据记录，CSV 标题不计入，也不冒充多行 CSV 的物理行号。
5. 核对参数化 `INSERT OR ABORT` 模板和准确目标，输入 `main.表名称` 后执行一次整文件事务。任务中心及设计器展示请求数、已确认处理数和提交／回滚／未知事实。

只读连接可检查和预检，不能写入。导入配置、映射和样本仅留当前窗口；关闭后不持久化，也不自动恢复导入。

## 值与事务语义

映射类型为文本、有符号 64 位整数、有限 REAL、Hex BLOB、Base64 BLOB 或布尔。JSON 数字沿原读取器保留文字；嵌套对象／数组转成保留数字原文的 JSON 文本。JSON 空键可以明确映射；缺失已映射的自有字段报错，不用 NULL 或默认值替代。NULL、空串和未映射目标互相独立，CSV 沿原 `\N`／转义约定。

整数不先转 Number；REAL 需通过十进制原文往返检查。精确小数、日期时间适合明确 TEXT 存储；目标数字亲和性可能改变文字或精度，不能通过 TEXT 映射暗中转换。STRICT ANY 保留动态类型，普通 ANY 仍按 NUMERIC 规则判断，依据 [SQLite 类型与亲和性](https://www.sqlite.org/datatype3.html)。

写入使用独立连接和 `BEGIN IMMEDIATE`，不借查询标签的临时表或事务。显式 `OR ABORT` 覆盖表约束默认的 IGNORE／REPLACE，防止静默跳行或删除冲突旧行；原表默认值、约束与触发器正常执行，依据 [SQLite 冲突处理](https://www.sqlite.org/lang_conflict.html)。每条原 INSERT 完整确认后读取顶层 `changes()`，避免把触发器写入数算作源记录数；任一错误在唯一 COMMIT 前整批回滚。原生失败明细只返回固定原因及能确认的源记录位置，不回显字段值、驱动原错或文件路径。

## 来源与资源保护

- 四个固定 IPC：`sqlite.tableImport.inspect`／`preview`／`apply`／`release`。公开输入没有路径、SQL、连接对象、操作编号或持久化回调。
- Main 绑定原文档、连接修订／代次及原文件令牌对象和路径摘要。显式释放同步撤权；旧请求晚回不能重新签发能力。检查和预览的 TTL 独立，领取后长任务不因 TTL 到期被中断。
- 原文件绑定设备／节点、大小、纳秒时间及完整 SHA-256。每轮沿同一流读取并核完整字节，不只验证样本。来源不得是目标库及其日志，也拒绝对应硬链接。
- 本流程在同一原字节链按所选编码严格检查，并在 EOF 验证尾部；非法字节不能靠替换字符通过预检。合法 U+FFFD、NUL 及非 BMP 字符正常保留；这个内部开关不扩展公共输入，也不改变旧 MySQL 导入的默认容错设置。
- 检查及预检的目录核验使用独立短只读快照，正常关闭／退出后才继续文件扫描；预检前后复核原目录，正式事务锁内再次核文件、目录版本和表定义。
- COMMIT 前同步保存最小事实，原提交 ACK 不因最终响应、磁盘概要或关闭失败被抹掉。COMMIT 可能发送及未知阶段不再开放停止；关闭、卸载和退出等待原承诺，不自动重试或重放写入。
- utility、文件流及在途请求纳入原连接的 pending／resources／取消／关闭账本；未确认资源隔离保留，不凭超时或取消意图宣称释放。

当前预算：源目录 1,000 字段、源名称 256 字符；目标 1,024 列、最多 128 映射；原标量 128KiB、最终单值 64KiB、整行 1MiB；样本 20 条／256KiB；每类能力 64 项、总预算 64MiB、领取期限 5 分钟；最多 1,000 万条记录、两个活动导入任务。预算不表示这些规模已经完成性能验收。

## 验证与剩余范围

WIN11-TEST 本轮不可达且未派发任务，按既有授权使用本机 Windows 独占合成配置；不访问 Server-200、剪贴板或已安装客户端数据。源码、原生窗口、安装包和平台结果分别记录，不以单元数量代替实际流程。

首轮 Main／任务 UI 的 120 项通过、2 项失败分别保留：任务列表夹具误设插入顺序，以及畸形预览回包未回收能力；按准确行为修正夹具，并修复产品回收。新增 COMMIT UI 用例最初遗漏合法 writing 阶段，补真实事件顺序后原错误身份／迟到断言保留。首次全图类型发现并发常量引用和泛型窄化错误，另有两处测试类型，均单独修正；没有放宽原超时、业务断言或资源保护。

真实磁盘后端首轮 19 例及其它七文件共 156 项通过，含 513 行、两格式精度／NULL／BLOB／默认／生成列、STRICT ANY、末条冲突、文件与目录改变、原事务隔离、取消、COMMIT 回包丢失和关闭未知。随后新增严格编码真实来源及最终发布回收，Main 共 44 项；中间候选原件保留，不冒称最终代码证据。

严格编码专项另揭示共享读取器的真实分块丢字问题：UTF-16LE 的两个代理项会被下游逐块转 UTF-8；GB18030 解码器在小块补完四字节字符时可能少分配输出。修复只缓存一个末尾高代理项及最多三个 GB18030 原尾字节，让完整序列再交原解码映射，不更换字符集表或加载全文件。四项最初失败及四项中间 GB18030 失败保留；原单字节分块和原文断言未改，39 项编码回归通过。新增向量夹具的数组展开错误和类型回调参数也独立修正，不冒称产品失败已凭夹具改动解决。该共享修复同时作用于原 CSV／JSON 读取，SQL 文本读取未改。

最终 `pnpm build` 严格类型及构建通过，Vite 部分 38.74 秒。`pnpm exec vitest run --maxWorkers=4` 为 1,049 文件、21,450 项通过，另 1 文件／1 项 POSIX 用例因 Windows 平台跳过，原 5 秒期限保持。
