# 备份归档与原子文件适配

`DatabaseBackupAtomicArchive` 已把固定两条目归档 writer 接到真实 `AtomicFile` 协议，提供 `open/writeDump/finish/commit/abort/snapshot/releaseTarget`。它属于私有执行端，路径、目标预留、任务身份及文件授权均由协调器提供，不能从 renderer 接收文件路径或资源证明。

## 文件与目标占用

`AtomicFileTargetReservation.reserve` 使用现有父目录归一化及全局目标互斥，在创建文件之前预留目标。可选预留只允许准确路径、一个 writer 领取一次。带预留的 `AtomicFile.dispose` 不归还外层目标锁；所属适配器必须确认原句柄关闭、临时文件删除或成功替换，再显式归还。因此未知备份不能被普通 CSV/JSON/XLSX 写入复用同一目标。普通未传预留的调用继续使用原自动归还路径。

适配器同步登记原目标预留 Promise，所有文件分配、原句柄及关闭/删除 Promise 都保留在同一实例。即使 AtomicFile 内部清理失败后丢弃引用，适配器仍保留原句柄事实。背压写入未离开时只返回未知，不并发关闭文件；取消在写入离开后再显式清理。没有句柄返回的 open 失败保持未知，不凭异常类型猜测文件资源已消失。

## 提交边界

只有完成 dump、manifest、目录和 ZIP64 尾部后才能提交。文件的 sync/close 完成后进入不可取消的 rename 边界。边界已开始但 rename 未确认或拒绝时，不再删除临时归档、不能释放目标锁；晚到 rename 成功则如实报告 `fileCommitted:true`。成功提交后取消只确认已结束的本地资源，不撤销已发布文件。

`snapshot.closed` 是本地事实，不代替执行器要求的显式终态回执。owner 的原对象及编号被永久绑定，观察到编号漂移后即使恢复也不能复活旧能力。目标预留及资源终态仍需接入 B01 执行器和任务记录，适配器本身不取得数据库锁、不运行原生工具，也不证明远端操作或恢复成功。

## 当前验证

新适配器九项和四个既有 AtomicFile 相关文件共 53 项通过，覆盖短写、原值保留、背压取消、关闭未知、rename 未知与晚到成功、目标互斥和身份撤销。数据/句柄/替换使用 RAM IO，父目录只读归一化复用真实 AtomicFile。首次类型检查在单测 UUID 推断上失败，原错误保留；修正为新 UUID 与准确原 UUID 后，仅补验 owner 场景一项（其余八项未选），最终类型通过。

53 项原件 SHA256 为 `e9e7dc0b6110487b340a60bfc779e22424353a78114dee956243505ef825c406`，owner 补验原件为 `3b46030d1e4f4d43713a178a1e7e91321305b4d29f07cc8a82c16d9ef92a0cba`。RAM 夹具回收只用于测试隔离，不把未知情形算作真实文件收尾通过。真实文件写入、独立容器读取、执行器组合及数据库备份继续分层验证。
