# MySQL／MariaDB 原生整库 SQL 备份

1. 在「工具 → MySQL／MariaDB 整库备份」选择已保存的直连数据库连接及要备份的库。
2. 用系统选择器选本机数据库客户端安装中的 `mysqldump` 或 `mariadb-dump`。工具系列及主版本需与源服务器一致。
3. 选择 `.sql` 保存位置，确认备份期间避免数据库结构变化，再开始备份。
4. 保存后可在「工具 → 执行 MySQL／MariaDB SQL 文件」选择该文件。脚本含原库名的建库与 `USE` 语句，恢复前应核对 SQL 和目标连接并使用空库或尚未创建的库。

备份使用原生客户端生成 UTF-8 SQL，包含 InnoDB 表结构及数据、视图、存储过程、函数、触发器与事件。保留脚本中的库名、对象定义和 `DEFINER`。源账号需具备足够的直接全局权限，客户端会检查对象的可见性。源库含非 InnoDB 基本表或不支持的关系类型时，备份会在写入前停止。跨实例恢复时，目标服务器所需的账号、授权、全局表空间和数据库外部依赖需另行准备。目标事件调度器已开启时，恢复为启用状态的事件可能按计划运行。

表数据使用原生工具的一致性快照。开始和结束均核对目录，但目录复核只能发现可观测的变化。备份期间需避免 DDL 和对象定义变更。取消会停止原生客户端，等待资源收尾后清除临时文件。MySQL 使用任务专用命名锁复核原服务器线程。MariaDB 的取消界面以本机客户端退出为准。临时凭据目录先校验访问权限，密码不会写入进程参数。原生工具成功退出、核对转储头尾并关闭检查连接后，才提交备份文件。[MySQL 原生转储说明](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html) · [MariaDB 原生转储说明](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump)

本节验收覆盖直连 TCP。连接使用 TLS 时，按保存的连接配置设置验证和客户端证书。SSH 入口和严格 TLS 的适用条件见[通过 SSH 备份整库](mysql-ssh-database-backup-20261107.md)。ZIP 归档写入与归档直接恢复继续。

## 2026-11-07 验收

- Windows 测试虚拟机不可达，本轮使用 macOS arm64 源码 Electron 和 Node.js 24.17.0。MySQL 8.4.11 和 MariaDB 11.4.13 实例位于 Server-200 隔离容器，由外部 SSH 端口转发至本机回环地址。应用使用直连配置。
- 从正式菜单分别选择 MySQL 8.3.0 的 `mysqldump` 和 MariaDB 11.4.13 的 `mariadb-dump`，生成 SQL 后用产品自己的 SQL 执行入口恢复。MariaDB 客户端和 OpenSSL 来自摘要校验过的 Homebrew 工具包，在隔离目录调整动态库路径以运行测试。
- 备份前与恢复后独立查询的表、视图、例程、触发器、事件数量，以及无符号 64 位整数、35 位定点数、中文、emoji 和二进制值均一致。恢复脚本中的视图和函数也能查询。
- 非 InnoDB 来源在写入前拒绝，保留原有同名文件。MySQL 原生客户端在表锁等待时取消，核对原任务的命名锁消失且原有目标文件字节一致。成功、失败和取消结束后均无新增临时凭据目录。
- 首轮双实库测试发现，服务器为例程创建者增加的单对象授权会被旧全局权限解析规则拒绝。修复后，附加授权与全局证明分别处理，角色与部分撤销仍不能充当权限证明。
- 共用原生进程代码的 PostgreSQL 18.6 回归通过 4 个源码 Electron 用例，覆盖纯文本、归档、直接恢复及原有 TLS／SSH 路径。所有测试容器、回环转发和测试账号会话均已清理。
- 使用要求 TLS 的测试账号复验了两套数据库。客户端成功完成加密备份和还原，MariaDB 的 `REQUIRE SSL` 授权后缀得到正确识别。该用例使用隔离自签名证书，证书身份校验、客户端证书以及 Windows 权限与安装包仍待单独验收。
- 定稿类型检查及源码构建通过。全量 Vitest 通过 1,358 个文件和 27,629 项，10 项按环境门槛跳过。普通直连、强制 TLS 双实库用例及 PostgreSQL 原生回归均通过。
