# 表关系图真实 Main／数据库验收

## 范围

用户明确授权 Server-200／13384 的两个准确随机 ER 隔离库后，核主机身份与原 MySQL 8.4.11 实例，按原计划仅创建六表：源库 `__owner`、parent、unlinked、child，目标库 `__owner`、parent。只有两条用途标记，业务表为空；不创建用户、不修改其它库。准确库名、owner、UUID、SQL、定义和行值原件仅保存在私有缓存，不入仓库。

使用真实客户端、Main、数据库驱动与正式关系图入口，消费 Root 已预置资源；测试自身只做 SELECT／SHOW 和本例本地连接／布局准备，不模拟元数据或数据库回包。Windows 优先虚拟机但本轮不可达、未派发，按既有授权本机使用独占临时 profile。

## 最终结果

原完整实库整例 8.276 秒通过，保持 120 秒、worker1、retry0、trace off。

- 原连接只保留会话密码，真实表页打开后进入关系图。手动读取 parent／unlinked 后为 3 张已读表、1 个未读跨库目标、3 个外键；复合映射准确保持 tenant→tenant、parent_id→id 的原顺序，自引用及跨库声明分明，跨库目标保持未读，未向其它库投递元数据。
- 刷新沿六个独立任务读取 child／parent／unlinked 两轮，目录一次、准备数据页一次；显示／缩放和关闭没有追加用户 SQL 或其它页。原设置完整保持，页面错误、越界请求与业务写入为零，截图已审。
- 用独立只读观察连接前后核六表完整定义、用途标记及全部行值保持；准确原 App 正常 exit0，观察连接及底层 socket 正常关闭。独立 CIM 核原 App／直接子进程不存在，成功 profile 已移除。
- 再核 owner、全部定义／行值、四条列映射依赖、无额外表／视图／例程／触发器／事件、零占用及零元数据锁，才先精确删除源库，再复核目标库并删除。最终两准确库均不存在，无用户或其它资源操作。

原件在私有 `.cache/relationship-live-20261103/`：原三轮日志、成功报告／截图、独立资源回执、预置及精确清理记录，未覆盖失败原件。

## 保留的原失败与修正

第一轮把网格骨架当成原页就绪，菜单仍是旧禁用状态。第二轮补原元数据及刷新可用检查后已完整读图，但验收白名单漏了工作区恢复和系统空握手，错误提示挡住关闭按钮，仍保留失败。

最终只补固定 `workbench.get`、`workbench.protocolReady`、`workbench.protocolTake` 的空参数入口；握手必须无 pending／active，领取必须为 null，不允许解析、提交或导航任何外部对象。原数据库白名单、六个任务、设置保持、正常退出和资源断言都未降低；新增只读失败审计便于核对，原期限与零重试不变。29 项环境门及 4 项默认／列举门单次通过。

这只证明 Windows／MySQL 8.4 的本组元数据和空业务表工作流；其它 MySQL／MariaDB 版本、限权、并发 DDL、Mac 实库、安装及完整模型正反向工程另验，E01 保持部分，暂不发布。
