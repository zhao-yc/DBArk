# 执行历史耗时范围筛选

## 使用与语义

从“历史与查询”打开执行历史，填写“最短耗时（毫秒）”或“最长耗时（毫秒）”，再明确搜索。两端都包含，可以只填写一端、填写0或使用相等端点；双端空白表示不限。输入必须是0至`Number.MAX_SAFE_INTEGER`的整数毫秒，不接受负数、小数或指数形式，不自动四舍五入。

比较直接使用历史记录中的原`elapsedMs`，其小数部分保持原值；不会重新计时、重发SQL或推断服务器耗时。本地记录反映客户端原执行测量，不能等同于服务器执行计划的估算成本。清除耗时只改变本面板草稿，原时间、来源、结果与正文条件保留，须重新搜索才生效。

## 分页与错误

耗时范围与现有时间、来源、成功/失败、完整SQL/错误文字条件共同生效。IPC严格校验后由原匹配工作线程逐条检查，不额外读取全量历史、不改变SQLite结构、最近1000条保留上限、25条扫描批次、字节预算或排序。

原始记录及时间/来源索引仍先验证，损坏记录按原“继续/停止”政策报告，不能被耗时条件静默隐藏。启用范围时负耗时是无法判断的记录错误；省略范围保持旧请求行为。翻页只接受原单次cursor和新taskId，客户端不能通过续页篡改已固定范围；历史或连接修订变化仍使旧页失效。

范围草稿进入完整筛选标识。修改后不能续读旧范围；非法输入在释放原cursor之前拒绝，保留原页面、原文字及原句柄。关闭、取消、迟到响应、续页释放和真实线程终态沿用既有生命周期。

## 验证边界

合同与边界、真实SQLite/工作线程分页、ReactDOM原事件及独立Windows界面分层验证。原生专项默认关闭，列表模式不加载桌面或读取配置；显式运行使用独占临时profile和清楚标记的合成历史，不建立数据库连接。独立SQLite读回与原始日志另记录，不能将离线样本称为真实数据库执行或安装包验收。

本机Windows最终严格类型检查通过，新构建39.10秒完成，637个产品输入文件摘要前后相同；完整672文件、13315项通过，1项POSIX条件跳过，288.62秒，退出0。新后端47项、旧分页19项、界面及输入55项、原生门37项分别通过；这些定向计数与完整执行重叠，不能累加。独立Python读取器17项合成正反自测通过，仅验证读取器，不等于原生整例成功。

原生整例固定58条合成历史、10次明确搜索、13次续页、3次精确释放，正常退出仅允许一次原空标签配置刷新。实际profile原SQLite只读核对身份及SHA；产品`LocalStore.open`含迁移副作用，只允许在独占副本上验证，另由Python `sqlite3` 直接只读原件。物理数据库会话未测，Main审计只证明本例没有转发数据库命令。
