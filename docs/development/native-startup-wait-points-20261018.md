# 原生启动原等待边界：有界相对时点

基于Root0.23固定 `ff462366e2f7fbba06ced95e1048aa4404da68eb`。本次仅扩展原显式进度观察，供区分安装专项在何处等待；不认定run1730的产品根因，不新增真实运行或CI。

## 附件字段

原“原生启动有界观察”JSON附件增加可选 `waits`：

```json
{"version":1,"points":[[0,1,40],[1,1,70],[2,1,75],[4,1,75]],"dropped":0}
```

每条为 `[阶段号, 调用序号, elapsedMs]`，只含有界整数：

| 阶段号 | 原等待边界 |
| --- | --- |
| 0 / 1 | 原 `verified()` 扫描进入／返回 |
| 2 / 3 | 原窗口设置前的 `source()` 进入／返回 |
| 4 / 5 | 该来源读取的原 `application.evaluate` 进入／返回 |
| 6 / 7 | 该来源读取的原 `identity.assertActual` 进入／返回 |

扫描和来源各用自己的连续调用序号，范围1至8。原正常双启动中扫描为1至6；来源1、2分别是首owner的runtime launch来源、controller.record来源，来源3、4对应第二owner。窗口准备／正常退出阶段的来源读取不扩入这组启动轨迹。原扫描内部全部walk/read/hash仍原样执行，阶段0/1表示原verified边界，不改写其内部检查次数。

例如最后为 `[4,2,...]` 且没有对应5，表示已进入第二次主进程来源evaluate，尚未观察到通过原guard后的返回；最后为6而没有7，表示实际来源路径核验尚未观察到返回。缺失返回点还可能是原期限或墓碑拒绝，不能越权补写或把它当产品故障证明。

## 权限与上限

沿用 `DBARK_NATIVE_EDITOR_PROGRESS=1` 且非list的原门；没有新参数、环境权限或RPC。默认关闭/list不建立等待记录器、不读取新缓存、不新增IO。每个记录调用紧跟原有guard，或在其后的连续同步代码内，只读 `elapsedMs()` 已验证缓存和本地停链状态，不调用新的权限门、时钟、文件检查或SDK；不改变任何原await的先后顺序。

轨迹每个TestInfo最多64条，满后丢弃计数封顶1024。没有有效缓存时不补造时间；阶段/序号或时间超界不记录。elapsedMs范围0至119999，不记录绝对时间、URL、路径、错误/SQL正文。它是原门最近验证的相对时点，不是独立高精度性能采样。

轨迹为run级纯内存数据，因而第一次launch之前扫描等待也可保留，即使尚无owner。afterEach原scope先retain的顺序不变，附件收集首先封存轨迹；迟到await仍须先经过原guard，墓碑后不能补写旧case，也不能得到退出、PID或清理权限。

继续复用同一个附件和原8192字节总上限，不单独扩大附件。原每owner4页／32事件、两个owner和最后一条数字来源记录的上限不变。旧完整数字来源／所有时间字段／最长事件及URL分类／各1024丢弃的最满形状为7226字节；全局64条紧凑轨迹（不是每owner64条）及其1024丢弃计数一并实际序列化后为8106字节，仍低于8192，不删旧证据来迁就。故障注入的超预算形状仍在附件IO前拒绝，并保留原错误。没有等待记录时附件原形状保持；没有owner观察和等待记录时不写附件。附件收集／序列化／写入失败与原TestInfo错误共同保留，不吞原错误。

原120秒、录制off、所有逐文件walk/read/hash、两次来源读取、真实来源门、正常退出握手、PID消失与目录清理守卫、成功消费者均未改。`identity.assertActual`仍只执行原实际路径核验，没有把它改成扫描或跳过它。
