# macOS 托管镜像更换后的重新核验

`8e3938c9` 的 CI run `40416673588`／arm64 job `121900639404` 运行在
`macos26 / 20261021.0445.8`（macOS 26.6.2／25G83）。原 keeper 仅准入
`20261013.0424.1`，在首次只读快照时拒绝，未生成候选计划，也未启动原生测试。
原收据记录 keeper 退出码 78、两种原生 CLI 结果为空；这不是产品专项失败。

先在 `main` 复用只读诊断工作流，编译 keeper 但不执行它，单次枚举 AppKit 矩形、
当前模式、全部 CG 模式及镜像关系，保留系统上下文和原始 JSON。新增的 main 入口
限定仓库、工作流、分支、push 事件及 inspect job；本机、自托管及其它工作流不准入。
该诊断不启动 DBArk，不切换显示模式，不构建或发布安装包。

只读 run `40418505118`／arm64 job `121906711558` 首次通过，但分配到了旧镜像
`20261013.0424.1`，不能作为新镜像证据。附件 `12695934650` ZIP 原件 SHA-256 为
`6c12b43c6396c5e18e211de290bbbc38a75fb433b67610c1cda0d9274eaa4d46`，
本地摘要与 GitHub 一致，全部条目 CRC 校验通过；完整 JSON 摘要为
`5e4e606b0186c55237adae25fd20f7744381d87cc3ced3f5ee0d5a6ff142f15e`。
它确认旧镜像单主屏、无镜像、scale1、12 个模式，未执行显示配置或产品验收。

由于托管池同时存在新旧镜像，常规 arm64 CI 的既有准备阶段也单次采集同一 runner 的
完整只读枚举，并随原失败现场上传。入口独立绑定原 desktop 工作流上下文，不修改环境
伪装身份；keeper 的未知镜像拒绝规则保持，不能用另一个 job 的旧镜像枚举补证。
