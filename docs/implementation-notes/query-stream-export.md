# Q05 任意 SQL 完整流式结果导出实施设计

## 状态与目标

本文保留 Q05 开发前的设计和五库研究依据，代码接口以 `src/shared/queryStreamExport.ts` 和 `query.exportStream` 为准。0.5.0 开发版已实现第一批 JSON 全结果/CSV 指定行集，实测进度见 [Q05 验收记录](../../tests/integration/acceptance-q05-query-stream-20261014.md)；本文后续建议不因此自动成为实现或发布结论。“导出已返回结果”仍只写出内存中已有的行，不重新执行 SQL；新的“完整流式导出”在同一查询标签会话明确进行一次新执行，完整结果直接写文件、工作台仅保留有界预览。

现有 `streamQuery` 会读尽服务器结果，但在显示行数和内存预算用尽后丢弃后续行。已经完成的截断结果没有可续读游标，不能从旧结果中补齐，也不能在旧导出按钮背后重跑语句。任何新的完整导出都属于一次新的数据库操作，即使模板与之前相同。

## 单次执行与会话边界

1. 打开窗口时捕获当前选区；没有有效选区时捕获全文。窗口内显示不可变模板、执行方式、目标文件和结果选择，随后编辑后台草稿不能改变本次请求。
2. 打开窗口、选择文件、切换编码及查看模板不执行 SQL。最后的“执行并完整导出”按钮是唯一数据库执行入口；同步入口锁防止双击重复请求。
3. 请求绑定查询标签已有的 `sessionId`。新标签尚未建立会话时，可由标签按现有方式明确建立一次；固定了执行会话之后，断线不自动换会话继续或重放。
4. 使用 `withSession` 和统一数据库任务互斥，保留当前事务、临时表、会话变量及用户当前库。不得复用整表导出的独立连接或主动建立快照事务。
5. 不自动 `START TRANSACTION`、`COMMIT`、`ROLLBACK` 或 `USE`。失败、取消和磁盘错误停止后续语句，已提交写入及 DDL 保留，未提交事务仍由用户明确处理。
6. 不凭 `SELECT` 首词判断没有副作用；函数调用、变量赋值、`INTO` 和程序调用等同样需要用户确认。也不为“列预览”或总行数先执行一次查询、追加 `COUNT`、`SELECT` 或其他诊断操作。
7. 状态不明时明确提示核对服务器。未知执行错误、超时、断线或文件失败都不能自动重试执行。重新点击开始必须显示“再次执行”及此前进度，不能包装成只重试文件写入。

## 第一实现的 IPC 契约

第一实现采用固定 `query.exportStream` 命令，文件路径仍由主进程通过用户文件令牌注入。以下为原设计草案，实际结构和预算以共享类型为准。

```ts
interface QueryStreamExportInput {
  sessionId: string;
  sql: string;
  taskId: string;
  fileToken: string;
  format: 'csv' | 'json';
  encoding: 'utf8' | 'utf16le' | 'gb18030';
  protocol: 'text-strict' | 'binary-explicit';
  resultSelection: { kind: 'all' } | { kind: 'row-result'; ordinal: number };
  parameters?: QueryParameter[];
}

interface QueryStreamExportOutput {
  statementsCompleted: number;
  results: {
    resultOrdinal: number;
    statementOrdinal: number;
    kind: 'rows' | 'status';
    rowResultOrdinal?: number;
    rowsWritten: number;
    affectedRows?: number;
    insertId?: string;
    warningCount?: number;
  }[];
  fileCommitted: true;
  transactionOpen?: boolean;
  transactionKnown: boolean;
  preview: QueryOutcome;
}
```

`rowResultOrdinal` 从 1 开始，只计有列定义的行结果集；`resultOrdinal` 还计 DDL/DML 和 CALL 最终状态包。两者在 UI、文件和日志中必须明确区分。CSV 的序号表示本次新执行产生的第 N 个行结果集，不保证与旧执行的结果按钮位置相同。

主进程校验令牌用途和格式，不能接受渲染端绝对路径。命令输入不携带完整结果数组；SQL、类型参数及选择字段有界，预览输出继续有界。类型参数在首条用户 SQL 前执行现有类型、名称和体积校验，历史只存模板，任务错误不保存可能包含实际参数值的服务器详情。

失败需要可结构化的进度信息：失败阶段为准备、执行、写入或文件提交，已完成语句数、当前结果及行数、文件是否提交、事务是否可知、SQL 是否可能已执行。涉及断线或执行阶段不确定时，`SQL 是否可能已执行` 必须保守为真。不能以“目标文件没生成”推断数据库没变化。

## 文件协议与多结果集

第一实现支持两种明确组合：

- JSON 全部结果：一个带版本号的封装，顺序记录每个行结果集与状态结果，不把不同结构的结果拼成一个对象数组。
- CSV 指定行结果集：输出用户指定序号的完整行结果。整个脚本仍执行一次，其他结果及状态被完整消费并在任务摘要说明，不能仅因已写完选中结果就忽略后续语句。

建议 JSON 结构如下，字段为设计草案：

```json
{
  "format": "DBArk-query-results",
  "version": 1,
  "results": [
    {
      "resultOrdinal": 1,
      "statementOrdinal": 1,
      "kind": "rows",
      "rowResultOrdinal": 1,
      "columns": [{ "position": 1, "name": "原列名", "exportName": "原列名", "type": "VAR_STRING" }],
      "rows": [{ "原列名": "实际值" }]
    },
    { "resultOrdinal": 2, "statementOrdinal": 2, "kind": "status", "affectedRows": 1, "insertId": "0" }
  ]
}
```

该封装不同于现有表 JSON 导入的对象数组，必须单独注明，不能暗示可以直接作为表导入文件。默认不把展开参数值或整个 SQL 正文附入文件元数据。

列处理复用 `resultExportColumns`：保留列顺序、原始名称及类型，重复和空名称映射为唯一输出名称，避开其他原始名称和已分配名称。内部按位置取值，不能依赖对象枚举顺序；合法的 `__proto__`、`constructor` 等列按普通自有字段处理。BIGINT/DECIMAL 和日期保持字符串，二进制沿用显式 Base64 对象；CSV 沿用现有 NULL、空字符串、反斜线及二进制协议。

若 CSV 指定结果不存在，或指定位置实际是状态包，明确失败并保留原文件；此前已经执行的数据库操作不撤销。CSV 的“全部结果”需要多文件容器、目录或归档及整体提交方案，列为后续缺项。首批不能用多个不兼容表头混写到单一 CSV 来宣称已支持全部结果，也不增加 SQL INSERT 导出目标表猜测。

## 流式通道、背压与预算

保留一套脚本调度器：`SqlScriptScanner` 每次取一条语句，依真实会话缓存模式继续扫描，类型参数绑定共享现有实现。结果消费者分为现有工作台有界结果和新的文件写入器，不维护第二套简化分号切分或 sql_mode 解析。

数据库事件转为有界结果帧：开始结果集、带结果序号的行、状态包、结束结果集。必须在协议事件边界固定行所属结果和列定义。不能以“最新列定义”解释已经排队的旧行，也要保留 CALL 最后状态包无结果编号的既有处理。

不在 `query.on('result', async ...)` 内直接异步写文件：事件发射器不会等待回调，容易并行写入、乱序或无限积压。异步消费者逐帧等待完整文件写入；队列达到行数或字节高水位时暂停驱动读取，消费后恢复。直接使用驱动行流也须补足结果编号和列事件关联，而非丢失多结果结构。

建议首批预算由共享常量管理，并通过压力测试确定最终数值：

| 项目 | 建议起点 | 超限行为 |
| --- | --- | --- |
| SQL 模板及展开后总量 | 各 20 MiB | 首条可提前判断时拒绝，动态后续超限停止 |
| 结果数量 | 200，包含状态包 | 明确失败，不丢弃后仍报告完整成功 |
| 单结果列数 | 1024 | 拒绝对应结果 |
| 原始单字段 / 单行 | 8 MiB / 16 MiB，另计 Base64 和编码后预算 | 明确失败，不截断文件行 |
| 待写帧队列 | 至多 8 行且 1 MiB；单个大行受独立行上限控制 | 施加背压 |
| 工作台预览 | 每结果至多 200 行、整个预览至多 16 MiB | 仅截断预览，文件继续完整写入 |
| 文件总量 | 首批建议显式 10 GiB 上限，实施前核对需求 | 达上限失败并说明，不能替换原文件 |

完整导出取消现有工作台 100000 行和结果数组总量限制，不将全部行跨 IPC 传输，也不拼接整个 JSON 文档。mysql2 会先接收和解析单个协议行，不能宣称大字段具备逐字节读取能力或恒定零分配内存。预算应在 Base64、JSON 和目标编码的大分配之前检查，并覆盖文件写入器自身的缓冲。

进度显示已执行语句、当前结果、已写行数和字节。没有总行数时使用不确定进度，直到文件提交才显示完成；不为了百分比重新扫描数据。

## 原子文件及取消提交点

从 `ResultFileTasks` 提取共用原子写入器：同目录随机临时文件、独占创建、完整消费短写、无损编码验证、文件同步、关闭、取消检查、原子替换和失败清理。现有“已返回结果”任务继续独立于数据库，不因复用写入器而获得 SQL 执行能力。

正常流程为：授权目标、建立临时文件、单次执行并写帧、完成全部语句、写封装尾部、同步关闭、最终取消检查、进入不可取消的文件提交点、替换目标、发送成功终态。必要时对同一目标路径登记活动写入，防止不同标签并发覆盖同一文件。

取消复用 `query.cancel` 的当前命令代次，不只设置 UI 标记。读取、磁盘写入、模式更新及下一语句之间都检查取消；取消控制连接尚未结束时保留会话锁，不能让晚到的 KILL 伤及下一次执行。磁盘失败也须停止并收尾当前服务器命令，不能仅关闭文件后把仍繁忙的会话交给用户。

原子替换开始后，晚到取消不能把已保存文件误报为取消。现有 `runTask` 返回前还会检查取消，新增流程必须把提交状态纳入统一终态判断。完成结果明确包含 `fileCommitted`；文件成功提交与数据库事务提交是两件独立的事。

失败或提交点前取消保留原文件并清理本任务临时文件。此前已执行写 SQL 的影响不因清理文件而消失，客户端不附加自动回滚或重放。

## 五实例协议研究及其限制

以下结论来自 200 服务器的隔离实测，不是 Q05 导出功能验收。使用 mysql2 原始驱动及项目当时的协议补丁，观察出站命令和准备阶段 EOF；只在探针进程包装观察方法，没有修改应用或驱动文件。每个实例创建独立随机库，结束时精确 DROP 并查询 `information_schema` 确认零残留，主连接与事务控制观察连接均退出。

| 端口 | 实际版本 |
| --- | --- |
| 13357 | MySQL 5.7.44 |
| 13380 | MySQL 8.0.46 |
| 13384 | MySQL 8.4.11 |
| 13310 | MariaDB 10.11.19 |
| 13311 | MariaDB 11.4.13 |

| 研究场景 | 精确结果 |
| --- | --- |
| UPDATE 影响 1 行后首次预处理 `SELECT ROW_COUNT()` | 五版返回 1；出站 PREPARE 22、EXECUTE 23 |
| 同一查询缓存命中 | 五版仍返回 1；只发送 EXECUTE 23，没有再次 PREPARE |
| `SQL_CALC_FOUND_ROWS` 返回受限行后读取 `FOUND_ROWS()` | 五版首次和缓存命中均返回预期总数 3 |
| CAST 非数字产生 1292 警告后，只成功准备一个新的 `SELECT 31337`，不执行它 | 三个 MySQL 的随后 SHOW WARNINGS 为空；两个 MariaDB 仍返回原 1292 警告 |
| 不支持的 PREPARE 后检查诊断 | 五版原警告被替换为 Error 1295，原 ROW_COUNT 从 1 变为 -1；FOUND_ROWS 仍为 3 |
| MySQL 准备 SHOW WARNINGS、SELECT @@warning_count、START TRANSACTION | 三版均 ER_UNSUPPORTED_PS 1295；只有 PREPARE 22，没有 EXECUTE 23。失败不会成为有效缓存命中 |
| MariaDB 准备 SHOW WARNINGS / SELECT @@warning_count / START TRANSACTION | 两版支持；首次及有效缓存命中的警告读取保留预期警告 |
| FLOAT 值 1 与 1.0000001192092896 | 五版文本协议两个值都成为 1；二进制协议保持两个不同值 |
| DOUBLE 值 1 与 1.0000000000000002 | 本探针五版均保持不同；不能据这一个例子保证全部文本浮点场景 |
| 预处理 CALL | 五版返回两个行结果集及最终状态包，FLOAT 相邻值仍可区分 |
| 事务内准备并执行查询 | 准备元数据 EOF 状态为 3，执行后事务仍活动；ROW_COUNT 为 1 |
| 事务内只准备 CREATE TABLE，不执行 | 五版未创建拟建表；独立连接仍读到已提交值 40，而事务内修改值 47 未暴露，未发生本次 DDL 的隐式提交 |

本机可复核材料位于 Git 忽略目录：`.cache/probe-q05-prepared.mjs`、`.cache/q05-prepared-protocol-evidence.json`、`.cache/q05-prepared-protocol.log`。证据项按端口与中文场景名称检索；这些本机文件不随公开源码包发布，本文结果表保留可持续引用的研究结论。凭据只来自本机忽略环境文件，不写入本文或输出。

准备元数据 EOF 含事务和模式状态位，但研究时的补丁只观察实际执行结果，没有为 PREPARE 元数据发状态事件。若后续补充，必须标明准备阶段，只按适用规则读取状态，不能把它当作用户 SQL 已执行；MariaDB 元数据警告数可为 0，而原 1292 警告仍存在，不能据此清空用户诊断。零列的准备响应也未必有可读取状态的 EOF。

## 文本严格模式与显式二进制模式

协议选择属于执行语义，不是可以隐藏的优化。首批建议分开两种模式，并在确认窗口说明：

- **文本严格模式**：默认不额外 PREPARE，保持现有文本查询执行和诊断语义。若遇到 FLOAT/DOUBLE 列且无法保证所需浮点精度，明确失败并说明本条 SQL 可能已经执行，保留原文件；不得把短小数当作完整底层浮点值。未来若另提供“按服务器文本表示导出”，须单独命名和说明它可能合并相邻 FLOAT 值，不能混称严格精度模式。
- **显式二进制模式**：用户确认可能新增准备操作，支持的结果用二进制协议保持浮点位。BIGINT/DECIMAL 继续为字符串，FLOAT/DOUBLE 为其 IEEE 数值，不把大 DOUBLE 因呈整数形状而误当作需要安全整数范围的 BIGINT。该模式不能承诺首次准备与缓存命中具有相同诊断行为。

诊断语句及已知不支持的控制语句必须在发送前选择文本路径，例如本次已测 MySQL 的 SHOW WARNINGS、SELECT @@warning_count 及 START TRANSACTION；完整范围通过词法识别和真实测试维护，不靠字符串包含判断。error_count、GET DIAGNOSTICS、SQL PREPARE/EXECUTE/DEALLOCATE 等支持差异继续单独验证。动态模式下仍遵守候选解析一致性要求，不能为了选协议猜测未知引号边界。

不能统一使用“先 prepare 探测，遇到 ER_UNSUPPORTED_PS 再文本 fallback”：即使证明没有发送 EXECUTE，错误准备自身也已经改变警告和 ROW_COUNT。第一实现对未覆盖的不支持准备应明确停止，不自动回退。准备成功也可能清警告，因此缓存命中测试不能代替首次执行测试。

若以后增加手动回退，必须让用户看到准备已改变诊断、此前语句进度及再次执行范围；不能仅靠错误码认定整个脚本尚未执行。EXECUTE 已发送或阶段无法确定时，任何异常都不得自动重跑。

## CALL/NBE 的 0.4 修复与 Q05 的继承边界

本次研究还发现：例程内改变 `sql_mode` 后，退出时可报告恢复后的完整模式为空，但最终状态及后续 EOF 仍带内部的 NBE 位。把该位直接重新标为可信，曾导致字符串里的 `:ghost` 被当成参数替换。

此问题已经归入 0.4 的会话协议修复，不列为 Q05 已实现功能。当前 `observeSessionState` 在完整模式与同包 NBE 位矛盾时持续标记模式未知；后续普通 EOF 只恢复可证的事务状态，不恢复词法信任。扫描器使用 NBE 与 ANSI 的四种候选组合，仅放行语句边界及参数位置一致的模板；明确报告且与状态一致的模式设置才恢复信任。

旧复现材料 `.cache/q05-call-state-engine-evidence.json` 记录的是修复前问题，不能当修复成功证明。独立的新回归在 `tests/unit/session-state.test.ts` 及 `tests/integration/engine-parameters.integration.test.ts`，覆盖跟踪开/关、普通 CALL/SQL EXECUTE、后续陈旧 EOF、字面参数歧义拒绝及明确模式恢复；五基线最终记录在 `.cache/p0-references-final-13357.log`、`13380.log`、`13384.log`、`13310.log`、`13311.log`。这些是协议修复证据，不是完整流式导出或新安装程序的验收。

Q05 必须复用这套状态观察和扫描逻辑，不因切换二进制执行重新信任准备元数据的陈旧 NBE 位，也不追加诊断 SELECT 来“修复”模式。

## 完成验收与明确后续缺项

必须完成以下真实验收后才能宣称 Q05 首批可用：

- 原脚本包含计数写入时，数据库只改变一次；打开窗口和模板预览不改变计数，文件失败或取消后不重放。
- 同一标签事务、临时表、变量及连接号保持；未提交数据可见，结束不自动提交或回滚，其他标签独立。
- 动态 sql_mode、四候选歧义、多语句、多结果 CALL、状态包及结果编号无串流；结果后续失败明确保留已提交部分。
- 百万行直接流式输出，内存与预览有界；数据超过显示上限时文件仍完整，超硬预算明确失败而非静默截断。
- 重复/空列名、合法原型同名列、BIGINT/DECIMAL、日期、NULL、空字符串、二进制和相邻浮点按所选模式验证。
- 首次准备及缓存命中分别验证诊断；不支持准备不发送 EXECUTE，不进行透明回退；执行错误、超时和断线不重试。
- 磁盘短写、编码失败、空间不足、真实长查询取消、写入期取消、原子替换期晚取消及退出都释放资源，原文件保护与终态一致。
- 真正 CSV 序号选择和不存在结果、JSON 全部结果、参数隐私、双击执行、模态快捷键、旧结果按钮不重跑均有真实 UI 断言。

后续缺项保留：CSV 多结果文件容器及整体提交、该 JSON 封装的导入/恢复、文件断点续写、已经完成查询的服务器游标续读，以及更宽的协议兼容范围。第一实现不以 SQL 入口或导出窗口占位宣称完成，也不把既有“导出已返回结果”计为完整流式执行。
